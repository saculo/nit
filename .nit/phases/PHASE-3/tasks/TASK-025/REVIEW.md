  <architecture-conformance result="pass">
    This is the task that closes the ADR-0004 contradiction, and it does so properly rather than
    cosmetically. The v1 skill's first rule — "only you dispatch agents" — had been false since
    TASK-015, leaving two components believing they owned the same decision. The rewrite states the
    real division as a table and holds to it: orchestrator picks the task, supervisor picks the step.

    Deleting the engineer routing table rather than correcting the `devops-engineer` name was the right
    call and worth recording as a judgement, not a shortcut. The task scope said to correct the name;
    correcting it would have preserved a responsibility that no longer exists, since the archetype
    declares the role and the supervisor dispatches it. Removing the table is a larger change than
    asked for and a smaller surface than leaving it.

    The decision to invoke the planning skills directly rather than through a subagent is also sound:
    `nit:clarify`, `nit:phases`, and `nit:tasks` are interactive by design, and interposing an agent
    between the user and their own clarification questions adds latency and loses fidelity. Task
    execution is delegated; planning is not. That asymmetry is deliberate and explained.
  </architecture-conformance>

  <findings>
    - [major, fixed] RV-1 — the skill declared `allowed-tools: Read, Glob, Grep, Bash, Skill` while its
      second core rule is "Never write or edit a file". `Bash` grants arbitrary writes, and the skill
      contains no bash blocks, so the capability was both unnecessary and directly contradictory. A
      constraint the frontmatter contradicts is not a constraint; it is a request. Compare `nit:status`,
      which correctly holds only `Read, Glob, Grep`.
    - [major, fixed] RV-2 — AC-3's split route was satisfied on the orchestrator's side only. The
      receiving skill, `nit:tasks`, still described splitting as reading "the architect's splitting
      rationale" — prose from a v1 design step. It predates TASK-018 and had no notion of a blocked
      result, `needs-splitting`, or `detail.taskTypes`. The orchestrator would have handed it a shape
      it did not know how to read.
    - [note] Fixing RV-2 surfaced a gap neither skill covered: what becomes of the original task after
      a split. Both now say it stays `blocked` — superseded, not completed — and that closing it is a
      human decision. Without that, the natural reading is that the orchestrator should mark it done,
      which would be a state transition it is forbidden from making.
    - [note] The split rule now requires every acceptance criterion of the original to land in exactly
      one subtask or be dropped with the user's agreement. Splitting silently changes the contract
      otherwise, and nothing else in the workflow would catch it.
    - [note] The skill states three real limitations rather than failing opaquely, and all three were
      re-verified against the code during this review: `$detect` unresolved (TASK-028), the approval
      flag unread (TASK-029), and `architecture-decision`'s rejection routing targeting a removed step
      (TASK-027). This is the skill most likely to hit all three, since it is the only one that runs a
      whole project. Stating them is right, but it means the headline v2 entry point cannot yet run two
      of six archetypes end-to-end.
    - [note] With this task, every skill that routes on v1 prose artifacts is migrated. `nit:init` is
      the last v1 surface, and five hooks are now orphaned — up from three when TASK-026 was written.
  </findings>

  <finding-resolution>
    <item id="RV-1" result="fixed">
      `allowed-tools` is now `Read, Glob, Grep, Skill`. The core rule states the enforcement explicitly
      rather than asking for restraint. A test asserts the skill holds none of `Write`, `Edit`, `Bash`,
      or `NotebookEdit`, and was verified by re-adding `Bash` and confirming the failure.
    </item>
    <item id="RV-2" result="fixed">
      `nit:tasks`' splitting section is rewritten against the blocked contract: it reads the step's
      `output.json`, takes the rationale from `explanation` and the split from `detail.taskTypes`, and
      no longer refers to an architect's prose. Tests assert it names `needs-splitting`,
      `detail.taskTypes`, and `resultType`, and that the v1 phrasing is gone. The orchestrator's route
      now points at the step output rather than at the task alone, so both ends agree.
    </item>
